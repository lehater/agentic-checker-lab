# Checker product requirements

> Generated from Harness canonical knowledge. Do not edit this file directly.

## Purpose

Проверяемый синтетический прототип исследования сохранённых ACL.

## Requirements

### REQ-CHECKER-101

Оператор задаёт один конкретный поток: IP источника и получателя, протокол и порты источника и получателя.

Status: ACCEPTED

Sources:

- docs/scenario/owner-problem-brief.md#traffic-query

Rationale:

Один целостный входной контракт; поля не отдельные обязательства.

### REQ-CHECKER-102

Checker использует результат отдельного источника релевантности по двум IP: пары устройство/ACL, сохраняя сведения о местах применения; несколько ACL одного устройства различаются.

Status: ACCEPTED

Sources:

- docs/scenario/owner-problem-brief.md#relevance

Rationale:

Определяет охват поиска независимо от правил matching.

### REQ-CHECKER-103

Для релевантных пар Checker показывает все подходящие сохранённые правила, с их сведениями и action, группируя по устройству/ACL и сохраняя порядок строк снимка каждого ACL.

Status: ACCEPTED

Sources:

- docs/scenario/owner-problem-brief.md#stored-evidence

Rationale:

Единый выходной контракт: полнота совпадений, принадлежность и порядок — его грани.

### REQ-CHECKER-104

Checker явно сообщает отсутствие совпадений и не вычисляет общий end-to-end permit/deny verdict.

Status: ACCEPTED

Sources:

- docs/scenario/owner-problem-brief.md#interpretation-boundary

Rationale:

Отдельное ограничение интерпретации, которое может меняться независимо от представления правил.

## Non-goals

- Implicit deny не обязателен.
- Реальные устройства, действующий сборщик, сложная сеть, промышленное хранилище и полный vendor parser не нужны.
- Точный routing heuristic не принят; допускается имитация релевантности.
