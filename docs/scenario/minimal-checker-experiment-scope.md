# PDEC-CHECKER-006 — цель эксперимента и упрощённый сквозной Checker

**Статус: OWNER-CONFIRMED INTENT / EXPERIMENT SCOPING.** Дата: 2026-10-16.

## Главное назначение

Цель Agentic Checker Lab — проверить полный цикл инженерной разработки с Harness до работающего кода и независимых тестов, а не создать промышленную систему сетевого анализа. Избыточная доменная проработка препятствует эксперименту. Первый исполнительный вертикальный срез должен быть минимально работоспособным, синтетическим, быстро проверяемым. Это уточняет тактику, не подменяет ранее принятые канонические Product Requirements и не публикует lifecycle CURRENT.

## Замысел полноценного Checker — зафиксировано, но отложено

1. Пользователь задаёт IPv4 адрес источника и назначения, транспортный протокол, порты источника и назначения.
2. Периодически собираются и сохраняются ACL snapshots, таблицы маршрутизации и сведения об интерфейсах устройств. Сохраняются исходный порядок правил, устройство, идентичность списка доступа и его attachments: интерфейс, направление IN/OUT и при наличии глобальная привязка. На одном устройстве могут одновременно действовать несколько ACL.
3. Упрощённая гипотеза определения релевантного устройства: отдельно сопоставить оба IP с сохранённой таблицей маршрутизации устройства; если разрешённые для этих адресов интерфейсы различаются, устройство считают потенциально транзитным и кандидатом на релевантность. Это эвристика, а не доказательство реального пути пакета. Подробности маршрутизации, ECMP, policy routing, NAT, неоднозначности и исключения сейчас не проектируются.
4. Функция релевантности принимает Source IP и Destination IP, выдаёт устройства и имена/идентификаторы относящихся к запросу ACL. Отдельная функция получает snapshots для этих пар. Все подходящие строки выводятся по устройствам и ACL с сохранением порядка snapshot. Не вычисляется итоговый сквозной Permit/Deny; отсутствие найденного правила не превращается самим Checker в implicit DENY.
5. Механизм определения релевантных ACL по интерфейсам/направлениям является самостоятельным открытым предметным вопросом для будущего настоящего Checker, а не условием текущего spike.

## Исполнительный первый slice — исключительно синтетический

- Вход: один JSON-запрос с пятью полями (src_ip, dst_ip, protocol TCP/UDP, src_port, dst_port).
- Synthetic relevance fixture: заранее заданные пары устройство + ACL + placement. Не вычислять маршруты и не симулировать таблицы маршрутизации ради видимости функциональности.
- Synthetic snapshot fixture: сохранённые в файлах наборы правил и метаданные их происхождения, даты и полноты там, где они известны; никакого оборудования, сетевых соединений, планировщика, настоящего snapshot collector или БД.
- Matching fixture: точные значения пяти полей (простое равенство); специально помеченная *экспериментальная урезанная семантика*, не нормативная семантика реальных Cisco ACL, подсетей, wildcard, any и диапазонов. Для полноценного matching Q-DV-002 остаётся открытым.
- Выход: все совпавшие строки по устройству и ACL в сохранённом порядке, с контекстом и известными метаданными. Сохранить различение «нет совпадения в имеющемся полном snapshot» и «не передан/неполон snapshot», не создавая третьего результата match.
- Независимые tests: 1 positive, 1 negative, 1 multiple matches and order, 1 two-ACL/device grouping, 1 missing snapshot. Expected outputs задаются вручную по fixture, не выводятся из кода.
- Реализация на простом локальном Python CLI с JSON stdin/file -> JSON output допускается как *выбор экспериментальной тактики*, не как утверждение общей архитектуры Checker.

## Exit criteria и дисциплина

Минимальный happy path: запуск приложения на fixture, детерминированный ожидаемый JSON, независимые automated tests, GitHub PR и зелёный CI. Отдельно зафиксировать время/сложность Harness, блокировки, ручные исправления, сколько реального кода сгенерировано и ограничения метода. Не проектировать больше того, что требуется для этого пути.

Не считать данное решение выполнением Q-DV-002 о реальной ACL-семантике, автоматическим принятием domain-use-case/verification-strategy или разрешением canonical publication blockers. Если строгий Harness требует иных условий для принятого consumer, честно обозначить experimental spike как не-admitted до соответствующего semantic admission. Не изменять принятые 13 требований задним числом.

Дальнейшее решение после первого работающего кода — продолжать ли к реальным предикатам и routing relevance на основании результата эксперимента, а не до него.
