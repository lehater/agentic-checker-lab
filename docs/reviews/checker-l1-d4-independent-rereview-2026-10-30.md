## 3. New findings (separate from F01–F06)

### N01 — P2 — Fractional UTC precision is unbounded but a lossless representation is not fixed

**Sources:** [validator `timestamp()` regex](https://raw.githubusercontent.com/lehater/agentic-checker-lab/27bda5bfc36cea79725a17f524bdcb99099868ac/tools/validate_checker_l1_input.py), [wire timestamp rule](https://raw.githubusercontent.com/lehater/agentic-checker-lab/27bda5bfc36cea79725a17f524bdcb99099868ac/docs/evaluation/checker-v1-contract-proposal.md), [D3 §4 output normalization](https://raw.githubusercontent.com/lehater/agentic-checker-lab/27bda5bfc36cea79725a17f524bdcb99099868ac/openspec/changes/checker-v1-baseline/design.md). The regular expression admits arbitrarily many decimal fractional digits; D3 and wire simultaneously promise not to drop **valid fractional precision**.

**Counterexample (standard library demonstration only, not Checker execution):** `2026-10-29T08:00:00.123456789+00:00` is allowed by the regex; Python `datetime.fromisoformat(...).isoformat()` renders `.123456+00:00` (nanosecond digits lost). The public linter only calls `datetime.fromisoformat` for validation and does not serialize a report, so this does **not** prove a currently executing bug; it shows a plausible simple implementation contradicts an explicit output obligation. **Required design action:** specify output timestamp as lexical UTC normalization preserving fractional text, or narrow fractional precision in *all* contracts/schema/validator/tests with product-scope review if necessary. Add `+00:00` fractional roundtrip case to acceptance ideas.

### N02 — P1 — Arbitrary finite JSON numeric `extra` may be silently rewritten (evidence fidelity gap)

**Sources:** [wire `extra` and original rule evidence](https://raw.githubusercontent.com/lehater/agentic-checker-lab/27bda5bfc36cea79725a17f524bdcb99099868ac/docs/evaluation/checker-v1-contract-proposal.md), [D3 `OriginalValidatedRule`, match table and input sequence](https://raw.githubusercontent.com/lehater/agentic-checker-lab/27bda5bfc36cea79725a17f524bdcb99099868ac/openspec/changes/checker-v1-baseline/design.md), [public `parse_document` using default `json.loads` float parsing](https://raw.githubusercontent.com/lehater/agentic-checker-lab/27bda5bfc36cea79725a17f524bdcb99099868ac/tools/validate_checker_l1_input.py), [owner D-004](https://github.com/lehater/agentic-checker-lab/blob/experiment/iterative-discovery-protocol/docs/discovery/checker/ledger.json). The candidate allows **arbitrary finite strict-JSON numbers** in opaque, display-only `extra`, which is to be returned as unchanged saved evidence. Its public parser validates finiteness, not exact numeric preservation.

**Counterexample (stdlib only):** input `{"extra":{"ratio":0.1234567890123456789012345}}` passes the finite-number rule, while ordinary `json.loads` followed by `json.dumps(...,allow_nan=False)` produces `{"extra":{"ratio":0.12345678901234568}}`. The wire JSON value has changed, despite being valid and display-only. There is **no Checker runtime**, and a future implementation could use a lossless decimal/lexical representation; the deficiency is that the proposed typed boundary does not require it. This is material because invented/rounded supplemental evidence can mislead the operator even though Checker is deliberately not interpreting that field.

**Required correction:** make the observation-fidelity guarantee and numeric representation explicit, e.g. parse accepted finite numbers losslessly (`decimal.Decimal` or retained JSON numeric lexeme), detach them, and implement strict finite JSON emission without mutation; alternatively **explicitly** bound precision/range of accepted numeric `extra` and update schema/wire/spec/tests. Do not solve by evaluating supplemental conditions or adding a vendor parser. Include a public contract case and subsequently an independently authored held-out case (not now).

### N03 — P2 — JSON Schema-only validation has a wider accept set than the normative linter

**Sources:** [schema `last_success_at` has only `format: date-time`](https://raw.githubusercontent.com/lehater/agentic-checker-lab/27bda5bfc36cea79725a17f524bdcb99099868ac/docs/evaluation/checker-v1-input.schema.json), [validator `timestamp()` and strict `type(v) is int`](https://raw.githubusercontent.com/lehater/agentic-checker-lab/27bda5bfc36cea79725a17f524bdcb99099868ac/tools/validate_checker_l1_input.py), [wire §validation](https://raw.githubusercontent.com/lehater/agentic-checker-lab/27bda5bfc36cea79725a17f524bdcb99099868ac/docs/evaluation/checker-v1-contract-proposal.md). A normal format-aware JSON Schema validator may accept `2026-10-29T09:00:00+01:00`, whereas the linter rejects it as non-UTC. JSON Schema's mathematical `integer` classification may accept number lexemes such as `443.0`, while Python's parsed `float` is rejected by `type(v) is int`. The wire already cautions that the linter performs extra checks: therefore **this is not a claim** that Schema alone was promised to implement cross-object/canonical checks. It is a portability hazard if builders treat Schema PASS as whole-wire PASS.

**Action:** define one normative validator/decoder as final gate in the contract, clearly label the schema as a **non-sufficient partial structural description** (including its timestamp and numeric-lexeme limits), and cover discrepant examples in public grammar checks. Optionally tighten the UTC regex in schema; do not create an additional validation framework. Treat schema-only PASS as *indeterminate* for full L1 validity.
