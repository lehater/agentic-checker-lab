## Question and evidence standard

Find the smallest existing stack that carries **approved product semantics → domain/architecture/detail design → independent review → tasks** without turning prompt instructions into fictitious machine-enforced approval.

- **Verified in source** means the exact upstream file or local main artifact was read at the revision below. It does **not** mean operational integration, semantic efficacy, or model compatibility was measured.
- **ADOPT** = recommend retaining an already-used capability as a D2 baseline; **ADAPT** = consider importing a narrow *idea or skill* after compatibility checks; **REJECT** = do not import this *entire candidate workflow* into the minimal stack. These are D1 engineering recommendations, **not owner approval**.
- No cross-tool, equal-task, independently scored benchmark was established by this source audit. Examples, self-reported outcomes, GitHub activity and schema validation are not comparative effectiveness evidence.

### Concrete integration and license risks

1. **Single workflow authority (P1):** `openspec/config.yaml` currently selects `spec-driven`. `intent-driven` and `anvil` are alternative root schemas, **not independent plugins to stack**. Swapping root schema rewrites workflow/artifact expectations; keep default unchanged for D1/D2 preparation. See [local config](../../openspec/config.yaml), [Intent schema](https://github.com/intent-driven-dev/intent-driven-template/blob/b5bda460a2180a55fc508fdedc4ef058d95355db/openspec/schemas/intent-driven/schema.yaml), [Anvil schema](https://github.com/jikkujoyce/openspec-schemas/blob/73eea60c622712a5d952ec1aec62da4e349f8c33/schemas/anvil/schema.yaml).
2. **False review gates (P1):** an author/reviewer prompt, `review.md` file, CI link and OpenSpec strict validation prove different things. If D2 adds a design gate, record `design/spec SHA → independent reviewer identity/context → findings → adjudication → accepted disposition`, and mechanically reject missing/stale review metadata where justified. Semantics still require independent judgment and source-trace checks.
3. **Installation/updates (P1):** Intent [installer](https://github.com/intent-driven-dev/intent-driven-template/blob/b5bda460a2180a55fc508fdedc4ef058d95355db/INSTALL_TEMPLATE.md) copies `openspec/`, `.opencode/`, `.agents/` and merges `AGENTS.md`; it explicitly does not handle upgrade tracking. Anvil [installer](https://github.com/jikkujoyce/openspec-schemas/blob/73eea60c622712a5d952ec1aec62da4e349f8c33/INSTALL.md) clones then copies a schema and selects it. Both risk overwriting an existing workflow; do not install wholesale. If future code is copied, pin origin, revision, local modifications and retain MIT/Apache notices as required.
4. **Cost and independence (P1):** Intent adversarial authoring invokes two OpenCode subagents; Anvil prefers a second model/read-only context. Neither has verified quality/cost gains in this project. Approve a bounded reviewer budget separately; never route private oracle content to implementation agents.
5. **Domain overfitting (P2):** DDD bridge's mandated context hierarchy, fixed scenario count and event/outbox constraints are design hypotheses for particular domains. For a small synthetic ACL query, begin with terms, invariants, flows, error contracts and inward module boundaries. Introduce aggregates, contexts or distributed patterns only for an actual invariant or integration requirement.
6. **Process collision (P1):** open [PR #54](https://github.com/lehater/agentic-checker-lab/pull/54) proposes overlapping `DS-*` planning. Accepted [PR #53](https://github.com/lehater/agentic-checker-lab/pull/53) already merged D0–D6 and S3D into the single roadmap. Do not promote a second lifecycle without explicit reconciliation.

## D1 recommendation: minimum D2 pilot (not implemented)

**Recommended minimal candidate:** existing OpenSpec `spec-driven` schema + [project engineering policy](../engineering/policy.md) + one *project-owned, independent design-review checklist* derived selectively from the candidates. Avoid installing any third-party schema or all nine DDD skills. C4 diagram/ADR only when a concrete boundary/durable tradeoff needs it.

**Bounded next experiment D2:** a docs-only synthetic design sample from *the already recorded proposed* Checker scope, explicitly labelled candidate. Read accepted source separately from proposal; produce (1) design with domain terms/invariants and one module/contract map, (2) a read-only independent review report with requirement/architecture trace, (3) a disposition table and tasks trace. Confirm the same artifact can be consumed by a new executor without inventing business behavior. Keep review and oracle independent; **do not** treat PR #51 as merged acceptance or run implementation.

**D2 pass/fail evidence to collect** (not achieved in D1): pinned CLI/schema compatibility; one sample's requirement → design → task links; explicit module/dependency checks and no extraneous abstractions; actual reviewer identity/input isolation/disposition; human confirmation of uncertain semantics; estimated context/iteration cost vs unmodified workflow. Prefer leaving `spec-driven` in place if an optional skill does not measurably eliminate a design defect.
