# Agentic SDLC — план интеграции готового стека проектирования

**Статус:** `ACTIVE_WORKPLAN` после включения в `main`. Это **план проверки**, а не решение об установке новых фреймворков, утверждение архитектуры Checker или разрешение запускать модели.  
**Дата:** 2026-10-29. **Владелец плана:** Agentic Checker Lab.  
**Начать в новом чате:** раздел [Recovery](#recovery--инструкция-для-нового-чата) ниже.

## 1. Зачем

Завершить воспроизводимый цикл **Discovery → Specification → Domain/Architecture/Detailed Design → Design Review → Tasks → Implementation → Independent Verification**, используя готовый стек, а не создавая собственный SDLC-фреймворк.

**Уже принятая основа проекта:** [Strategy](strategy.md), [Engineering Policy](../engineering/policy.md), [Governance](governance.md), [Discovery v0.1](../discovery/README.md). Управление изменениями — **OpenSpec** как существующий кандидат; AI-исполнитель — **OpenCode/Codex** по необходимости; ветви будущего сравнения — **Direct Codex** и **Microsoft RPG/CoderMind + Codex** на **одинаковых утверждённых входах**. Harness не возвращаем в активную схему.

**Рабочая гипотеза (не доказанный результат):** модульные готовые Skills / Config / Custom Schema, применяемые выборочно, позволяют закрыть недостающий этап проектирования с меньшей избыточностью, чем собственный полный процесс. **Запрещено заранее считать победителем какой-либо инструмент или архитектурную практику.**

## 2. Границы полномочий и действующее состояние

- **Канонический источник истины** — только принятый `main`; Draft PR — кандидат/свидетельство. Статусы и gates из [current-state.yaml](current-state.yaml) не отменяются этим планом.
- [Draft PR #51](https://github.com/lehater/agentic-checker-lab/pull/51) содержит кандидатную спецификацию Checker L1 и **запись явного утверждения владельцем границ синтетического MVP** от 2026-10-29. Это **не** означает, что PR уже слит или что зафиксированы независимый oracle, полная архитектура и E2E.
- [Issue #32](https://github.com/lehater/agentic-checker-lab/issues/32) — приёмка L1; [PR #48](https://github.com/lehater/agentic-checker-lab/pull/48) — историческое evidence Q/D, не автоматически принятый `main`.
- Подготовка *кандидатного дизайна* может идти параллельно независимой семантической проверке; **заморозка дизайна, oracle и начало генерации кода** запрещены до согласования источников, утверждения соответствующих артефактов и выполнения локального preflight.
- Новые неоднозначные требования возвращаются в Authority Gate; архитектор может самостоятельно решать только делегированные технические вопросы. Не переобозначать неразрешённую предметную семантику как «инженерный выбор».
- Не изменять AI Lab, не обращаться к реальным FW и не тратить лимит моделей на незаявленный эксперимент.

## 3. План с проверяемыми выходами

| ID | Этап | Проверяемый результат | Gate |
| --- | --- | --- | --- |
| **DS-01** | **Аудит готовых компонентов**, без установки: `intent-driven-dev/intent-driven-template`, `ForceInjection/domain-driven-design-skills`, `jikkujoyce/openspec-schemas` (Anvil), штатные механизмы OpenSpec | `docs/research/openspec-design-stack-audit.md`: точные repo/commit/version/license, реальные templates/skills/schemas/prompts/роли/проверки, их зависимость от OpenSpec и OpenCode, доказательства, риски, `ADOPT / ADAPT / REJECT` | Не считать README доказательством эффективности; не приписывать проектам несуществующие тесты; проверить версии и совместимость |
| **DS-02** | **Минимальная конфигурация дизайна** на базе OpenSpec | Один обоснованный кандидат workflow/config/schema: Domain Model → Design → Review → Tasks; указаны источники каждого заимствованного компонента; без дублирования владеющих спецификаций | По умолчанию использовать штатный `design.md` и `config.yaml`; custom schema/skills — только при выявленном недостатке |
| **DS-03** | **Проект Checker L1** по согласованной версии требований | Предметная модель и инварианты; границы компонентов и направленность зависимостей; контракты входа/выхода и ошибки; ключевые решения/альтернативы; минимальная диаграмма при необходимости; trace к D-001..012 и OpenSpec | Кандидатное проектирование до финализации L1 разрешено, но не объявлять его одобренным или готовым к codegen |
| **DS-04** | **Независимый Architecture / Design Review**, исправление замечаний | Отчёт по правильности границ, рискам, отсутствию лишних абстракций, полноте контрактов и соответствию принятым требованиям; результат `PASS / CORRECTIONS / BLOCKED / INCONCLUSIVE` с источниками | Независимость ревьюера и ограничение циклов исправлений; зелёная структурная проверка не доказывает правильности архитектуры |
| **DS-05** | **Финализация L1 + независимый oracle + локальный preflight** (см. [Issue #32](https://github.com/lehater/agentic-checker-lab/issues/32)) | Принятые хеши спецификации/архитектуры; изолированные скрытые input/expected acceptance fixtures и SHA; проверенные версии OpenSpec/Node/Codex | Held-out oracle не доступен агенту-разработчику; отсутствие реального evidence = `BLOCKED`, не `PASS` |
| **DS-06** | **Реализация/эксперимент** после всех gates | Direct Codex vs RPG + Codex на одной архитектуре, спецификации, oracle и сравнимых бюджетах; логи времени, числа исправлений, архитектуры и токенов (если подтверждены) | Отдельное разрешение на ограниченный модельный эксперимент, без подмены спецификации полученным кодом |

**Нужные практики, не шесть обязательных ритуалов:** элементы DDD (язык/инварианты/сущности) — по сложности предметной области; C4 — ровно полезные виды; ADR — только для значимых решений; контрактное проектирование — там, где есть значимые границы; Design Review — обязательный контроль для проекта, отправляемого в реализацию. Все практики **встраиваются в OpenSpec Design**, а не становятся конкурирующими источниками истины.

## 4. Как оценивать выбор готового стека

Для каждого кандидата DS-01 фиксировать **факт из исходника / интерпретацию / гипотезу**, не смешивать с измеренным результатом. Сравнивать практическую полезность: (1) покрывает ли отсутствующее проектирование, (2) трассировка и передача между этапами, (3) независимая проверяемость, (4) возможность применять выборочно, (5) накладные документы/токены/время, (6) лицензия и поддержка, (7) конфликты с OpenSpec и нашей Engineering Policy.

Не запускать девять стеков на одной задаче без задачи и бюджета. Сначала статический аудит готовых решений и одна **минимальная** предлагаемая конфигурация; лишь затем ограниченный design-пилот на Checker с замерами. Не считать авторские демо и произвольные LLM-баллы независимым сравнительным экспериментом.

- **Принято ранее в main:** стратегия без Harness; OpenSpec как кандидат для изменений; Direct Codex как baseline, RPG как экспериментальная ветвь; Clean Architecture/SOLID/KISS/YAGNI; Evidence-Gated Discovery v0.1.
- **Отдельное evidence:** утверждение владельцем пакета синтетического L1 зарегистрировано в открытом **Draft PR #51**. Состояние `main` и спецификации проверить заново, не переносить статус PR автоматически.
- **Не завершено:** DS-01..DS-06; аудит исходных репозиториев, выбор архитектурного стека, независимый design review, принятые oracle и E2E. Этот документ сам по себе не завершает ни один этап.
- **Единственное ближайшее действие:** **DS-01 — аудит реальных файлов и процессов трёх готовых сборок**, сохранить выводы в `docs/research/openspec-design-stack-audit.md` отдельным PR. Перед DS-02 показать обоснованное `ADOPT / ADAPT / REJECT` и минимальный набор, не устанавливать всё подряд.

## 7. Изменения плана

Обновлять этот **канонический план** через маленький PR; решения о выборе инструмента оформлять здесь (или ссылкой на ADR с указанием статуса), а подробную аргументацию сохранять в `docs/research/`. Не создавать параллельный «актуальный план» в чатах. После каждого завершённого DS-этапа записывать проверенный результат, SHA/ссылку на evidence, новый следующий шаг и blockers; синхронизировать [current-state.yaml](current-state.yaml) и [roadmap.md](roadmap.md) при смене активной фазы.
