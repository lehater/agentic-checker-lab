# Problem Evidence — Checker

Источник: [исходная постановка владельца](../scenario/owner-problem-brief.md).
Разработку, выбор Capabilities и проверки агенту поручил владелец в текущей задаче.

Оператору трудоёмко вручную искать сохранённые ACL-правила на множестве устройств.
Он хочет исследовать конкретный поток по IP источника/получателя, протоколу и
портам, получая все подходящие правила релевантных устройств, сгруппированные по
устройству и ACL и сохраняющие порядок строк снимка и action каждого правила.
Это свидетельства о сохранённой политике, а не общий end-to-end permit/deny.

Начальный результат — небольшой запускаемый прототип с синтетическими снимками
и имитацией источника релевантности. Реальные устройства не опрашиваются.
Устройство может иметь несколько ACL и мест применения; устройство не равно ACL.
Отсутствие совпадений сообщается отдельно от совпадений, без вычисления implicit deny.

Downstream: Product Requirements формализует наблюдаемые обязательства;
Domain Design определяет минимальные поддерживаемые предикаты; Architecture и
Interface Design выбирают реализацию и представление; Verification Design
задаёт независимые проверки до кода. Производственный сборщик, vendor parsing,
точная маршрутизация и промышленное хранилище не нужны для начального результата.
Будущий routing heuristic означает лишь потенциальную транзитность и сейчас
не принимается как достоверный алгоритм пути.

Противоречий, мешающих сформулировать проблему, в новой постановке нет.
Исторические admissions и предметные предположения не используются как требования.
