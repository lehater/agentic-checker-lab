## Exact published questions and owner-approved meanings

### Q-006

Published: Если оператор не знает фактический порт источника (например, клиент обращается к TCP/443 с динамического порта), что должно означать значение порта источника по умолчанию: проверку конкретного номера, отсутствие ограничения по этому полю или иной смысл? Какое поведение поиска вы ожидаете для правила, ограничивающего порт источника?

Approved normalized: Источник и получатель задаются одиночными IP-адресами, не подсетями; протокол выбирается из TCP/UDP. Оба порта могут быть конкретными значениями или any. Пустое поле каждого порта в интерфейсе означает any и является значением по умолчанию. any на стороне запроса снимает ограничение соответствующего порта при поиске ACL-правил, не требуя, чтобы каждое найденное правило охватывало все порты. Первоначально предложенное числовое значение источника 65535 отвергнуто.

Owner interpretation change: После первой нормализации владелец изменил ответ: вместо исходного дефолта 65535 для порта источника оба порта по умолчанию пустые/any. Первый D-009 был только предложен, не утверждён и не сохранён. Старые утверждённые D-001/D-004 не переписываем; D-009 уточняет семантику пяти параметров.

Example Mapping rule: Пустое поле порта в запросе означает отсутствие ограничения по этому порту.
Example: TCP 10.0.0.5:any → 192.0.2.10:443 может отобрать ACL-правила с исходным портом 55000 и с диапазоном исходных портов при совпадении прочих условий.
Counterexample: Пустой порт нельзя подменить 65535 и нельзя трактовать как требование, чтобы ACL-правило разрешало все порты.

### Q-007

Published: Если один и тот же ACL привязан к нескольким применимым местам на одном межсетевом экране (например, вход интерфейса и глобальная привязка), должен результат содержать одну группу ACL со всеми местами применения или отдельную группу для каждой привязки? Что оператор должен видеть, чтобы не потерять факт каждой привязки?

Approved normalized: На одном межсетевом экране одинаковый именованный ACL, имеющий несколько релевантных привязок, отображается одной группой с перечислением всех привязок. Совпавшие правила ACL не дублируются. Решение касается представления фактов, а не способа matching.

Owner interpretation change: Владелец назвал несколько привязок одного ACL редким случаем; выводить ACL по имени один раз, но не терять привязки.

Example Mapping rule: Один именованный ACL на устройстве отображается одной группой со всеми релевантными привязками.
Example: ACL WEB_IN применим на входе интерфейса и глобально: одна группа с двумя привязками и одним набором правил.
Counterexample: Две дублирующиеся группы без указания общей принадлежности к ACL либо потеря второй привязки не соответствуют ответу.

### Q-008

Published: При запросе от клиента к серверу (например, TCP 10.0.0.5:55000 → 192.0.2.10:443) должен Checker показывать только ACL-правила для указанного направления или дополнительно искать правила для ответного направления (192.0.2.10:443 → 10.0.0.5:55000)? Если обратное направление нужно, оно проверяется отдельным запросом или тем же?

Approved normalized: Один запрос Checker рассматривает только явно заданное направление соединения. Для обратного направления необходим новый запрос независимо от stateful-поведения конкретного FW. Возможная кнопка перестановки IP-адресов и, возможно, портов является только UX-предложением, без утверждённого контракта.

Owner interpretation change: Указание на stateful FW — объяснение, а не новое предположение реализации; инверсия в интерфейсе является необязательным предложением.

Example Mapping rule: Проверка заданного и обратного направлений выполняется отдельными запросами.
Example: 10.0.0.5:55000 → 192.0.2.10:443 и 192.0.2.10:443 → 10.0.0.5:55000 — разные запросы.
Counterexample: Нельзя автоматически объединять ACL-правила для обоих направлений в одном результате.
