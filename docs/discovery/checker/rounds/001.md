### Q-001

Exact published text: Опишите один характерный сценарий проверки потока, по которому вы будете судить о полезности первого прототипа Checker: какие устройства/ACL и совпадающие правила ожидаете увидеть и какой результат сочтёте ошибочным?

Approved answer: Цель — поиск правил политики доступа на отдельных FW по направленному соединению, а не проверка доступности. Вход: IP источника и назначения, TCP/UDP, порты источника и назначения; ICMP пока исключён. Порт источника можно задавать явно, его default не утверждён. Вывод: релевантные FW, входящие/исходящие интерфейсы, ACL, все совпавшие строки с permit/deny, в исходном порядке внутри ACL. Ни агрегированный end-to-end verdict, ни применимость правила ко всему соединению не вычисляются.

Owner correction: «Проверка потока» заменена предметным смыслом «поиск правил политики доступа», без вывода о фактической доступности.

Example Mapping rule: Показывать все совпавшие правила в сохранённом порядке.

Example: permit и deny в одном ACL совпали: обе строки в порядке снимка.

Counterexample: Показать только первую строку либо вывести итоговый permit нельзя.

### Q-002

Exact published text: Когда устройство лишь потенциально транзитное, но реальный путь потока неизвестен, по какому принципу считать его ACL релевантными с учётом привязок на вход, выход и глобально? Приведите пример ACL, которую следует включить или исключить.

Approved answer: По локальной маршрутизации к IP источника/назначения определяются интерфейсы FW. Если они различны, FW включается как потенциально транзитный; если совпадают, FW исключается в MVP. Для выбранного FW анализируются входные ACL входящего интерфейса, выходные ACL исходящего интерфейса и глобальные ACL. Исключения и более точный путь отложены.

Owner correction: Разные интерфейсы — приближённая потенциальная релевантность; применение входных/выходных/глобальных ACL.

Example Mapping rule: FW потенциально транзитен при разных найденных интерфейсах.

Example: Источник и назначение соответствуют разным интерфейсам: анализируем соответствующие ACL.

Counterexample: Один интерфейс для обоих адресов: FW не входит в MVP-поиск.

### Q-003

Exact published text: Как должен трактоваться результат для сохранённого ACL-правила, если у него есть дополнительное условие, которое нельзя проверить по пяти полям запроса (например TCP established или расписание): считать совпадение неподтверждённым, завершать проверку ошибкой или использовать иной подход?

Approved answer: Совпадение для поиска определяется пятью полями: IP источника и назначения, протокол, оба порта. Все дополнительные условия исходного правила (например established или расписание) показываются, но не интерпретируются и не проверяются. Совпадение по пяти полям — не вердикт о полной применимости правила.

Owner correction: Отвергнута постановка интервьюера о необходимости error/UNKNOWN для дополнительных условий: показывать правило и его исходные условия.

Example Mapping rule: Дополнительные условия не участвуют в проверке пяти полей.

Example: Совпало по пяти полям, присутствует established: исходное правило показывается.

Counterexample: Скрыть совпадающее правило лишь из-за отсутствия проверки established нельзя.

### Q-004

Exact published text: Какой предметный смысл оператор должен видеть в трёх случаях: релевантных ACL нет; релевантные ACL есть, но ни одно сохранённое правило не совпало; релевантная ACL известна, но её снимок отсутствует или неполон? Что оператору запрещено заключать из каждого случая?

Approved answer: Релевантный FW без привязанного ACL выводится без имени ACL; привязанный ACL выводится с именем и пустым списком, если по пяти полям нет совпадений (независимо от того, пуст ли сам ACL). Не выводятся implicit deny и вывод о блокировке. Неудачный сбор нового снимка логируется, но не перезаписывает последний успешный снимок и его дату; пользовательский поиск показывает имеющиеся данные, не сообщая об ошибке предыдущего обновления. Если не было ни одного успешного снимка, поведение инженерно не определено.

Owner correction: Пустое имя ACL = ACL нет; имя при пустом списке совпадений = ACL есть, но совпадений не найдено. Ошибки сбора отделены от поиска.

Example Mapping rule: Наличие ACL определяется его именем; пустой список совпадений допустим.

Example: ACL named OUT_ACCESS, ноль совпадений: имя показано, список пуст.

Counterexample: Подменить этим выводом отсутствие ACL или блокировку нельзя.

### Q-005

Exact published text: Какие сведения о происхождении и актуальности сохранённого ACL-снимка нужны оператору для правильной интерпретации совпадений в прототипе (например время получения, устройство, ACL, место применения), и что из этого действительно обязательно для первой версии?

Approved answer: У каждого ACL свой последний успешно сохранённый снимок и дата обновления. При полном опросе FW даты ACL могут совпасть; при раздельном — отличаться. Хранить историю не требуется. Ошибка опроса не меняет ни снимок, ни дату.

Owner correction: Собственная дата обновления каждого ACL, только для успешного сбора.

Example Mapping rule: Снимок и дата обновляются только после успешного чтения.

Example: Успешно 10:00; ошибка 11:00: остаётся снимок 10:00 и его дата.

Counterexample: Сделать дату 11:00 либо заменить снимок пустым недопустимо.

## Accepted decisions

- D-001 ← Q-001: Checker ищет и отображает правила ACL политик доступа по пяти параметрам направленного TCP/UDP-соединения, не проверяя фактическую доступность.

- D-003 ← Q-002: Для такого FW анализируются ACL на входном направлении входящего интерфейса, на выходном направлении исходящего интерфейса и глобальные ACL.

- D-005 ← Q-001, Q-003: Все совпавшие строки показываются в исходном порядке ACL, включая permit/deny, без first-match отсечения и без агрегированного вердикта.
- D-006 ← Q-005: Хранится только последний успешно полученный снимок каждого ACL с индивидуальной датой обновления; истории нет, дата отображается пользователю.
- D-007 ← Q-004: FW без ACL отображается без имени ACL; именованный ACL с нулём совпадений отображается пустым списком; пустой список не означает пустой ACL или блокировку.
- D-008 ← Q-004, Q-005: Ошибка чтения ACL логируется на этапе сбора и не перезаписывает последний успешный снимок/дату; поиск использует сохранённые факты, не сообщая о прошлом сбое.
