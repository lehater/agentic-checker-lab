**Status**: Draft — проектные допущения требуют отдельного подтверждения владельцем

## User Scenarios & Testing *(mandatory)*

### User Story 1 — Найти все совпадающие ACL-правила (P1)
Оператор задаёт IP источника и назначения, транспортный протокол и два порта. Система по полученным от отдельного механизма парам устройство/ACL проверяет сохранённые снимки и показывает **все** строки, подходящие под запрос.

**Independent Test:** На синтетических данных с двумя правилами, удовлетворяющими запросу, в результате присутствуют оба, даже если первое имеет action `deny`.

**Acceptance Scenarios:**
1. **Given** один релевантный ACL и два совпадающих правила, **when** оператор выполняет проверку, **then** показаны оба правила в исходном порядке.
2. **Given** релевантные ACL без подходящих правил, **when** оператор выполняет проверку, **then** явно показано отсутствие совпадений.
3. **Given** список релевантных ACL пуст, **when** выполняется проверка, **then** отображён пустой результат без домысла о доступности.
4. **Given** одно совпадающее `deny` и следующее `permit`, **when** выполняется проверка, **then** обе строки представлены без вычисления итогового verdict.

### User Story 2 — Сохранить контекст и порядок (P2)
Оператор видит, на каком устройстве и в каком ACL найдено каждое правило, исходное действие правила и информацию о месте применения ACL, если она присутствует в снимке.

**Independent Test:** Два ACL одного устройства и один ACL другого остаются раздельными; порядок правил каждого ACL не меняется.

**Acceptance Scenarios:**
1. **Given** одно устройство с двумя ACL, **when** оба релевантны, **then** они не объединяются.
2. **Given** правила снимка в порядке R3,R1,R2, **when** совпадают R3 и R2, **then** результат сохраняет порядок R3,R2.
3. **Given** места применения ACL (in/out/interface или global), **when** сформирован отчёт, **then** они представлены как метаданные снимка без вывода реального пути трафика.

### User Story 3 — Запуск на синтетических данных (P3)
Разработчик может проверить минимальный end-to-end сценарий, не подключаясь к сетевым устройствам, используя явно определённый поддерживаемый поднабор предикатов ACL.

**Independent Test:** Известный пример входа приводит к воспроизводимому отчёту; неподдерживаемая конструкция отклоняется явно, а не интерпретируется произвольно.

**Acceptance Scenarios:**
1. **Given** валидный синтетический набор снимков, **when** он обрабатывается повторно, **then** получается эквивалентный результат.
2. **Given** отсутствующий снимок для релевантной пары, **when** выполняется проверка, **then** система сообщает об отсутствии требуемых данных, а не считает ACL пустым (проектное допущение A-03).
3. **Given** неизвестную конструкцию ACL, **when** обрабатываются данные, **then** система сообщает об неподдерживаемом формате (проектное допущение A-04).

### Edge Cases
- Один firewall имеет несколько ACL; один и тот же ACL может иметь несколько placements.
- Совпадение может затрагивать первый/последний элемент диапазона порта или IP-сети.
- Повторяющиеся идентификаторы снимков/правил и некорректные параметры запроса.
- Пустые ACL, отсутствие релевантных пар, отсутствие совпадений.
- Необязательная информация о местах применения; она не используется как доказательство фактического сетевого пути.

## Requirements *(mandatory)*

### Functional Requirements
- **FR-001**: Система MUST принимать пять параметров потока: source IP, destination IP, protocol, source port и destination port.
- **FR-002**: Система MUST использовать список релевантных пар устройство/ACL, предоставленный отдельным механизмом; в первом прототипе он может быть синтетическим.
- **FR-003**: Система MUST получать сохранённый снимок для каждой релевантной пары; отсутствие требуемого снимка MUST быть диагностируемым (A-03).
- **FR-004**: Система MUST независимо проверять каждое правило по всем пяти параметрам потока с помощью явно указанного поддерживаемого поднабора предикатов.
- **FR-005**: Система MUST возвращать все совпадающие строки без остановки на первом `permit`/`deny`.
- **FR-006**: Система MUST сохранять исходный порядок строк внутри каждого ACL.
- **FR-007**: Результат MUST сохранять принадлежность правил конкретному устройству и ACL.
- **FR-008**: Каждое совпадение MUST сохранять исходное действие правила (`permit`/`deny`) как атрибут.
- **FR-009**: Результат MUST различать совпадения и отсутствие совпадений; он MUST NOT вычислять универсальный end-to-end permit/deny verdict или неявный deny.
- **FR-010**: При наличии сведений о применении ACL результат MUST сохранять интерфейс, направление или глобальную привязку как метаданные.
- **FR-011**: Прототип MUST работать с синтетическими данными без подключения к реальным firewall.
- **FR-012**: Поддерживаемый набор ACL-предикатов MUST быть явным; неизвестные варианты MUST не приводить к молчаливому совпадению (A-04).
- **FR-013**: Система MUST выдавать диагностируемую ошибку при некорректном формате входных данных, вместо правдоподобного частичного отчёта (A-05).

### Key Entities
- **Flow Query** — пять характеристик проверяемого потока.
- **Relevant ACL Reference** — ссылка на пару устройство/ACL, возвращённую внешним механизмом.
- **ACL Snapshot** — набор правил конкретного ACL с упорядоченными строками и placements.
- **ACL Rule** — сохранённый предикат потока, действие и идентификатор.
- **Match Report** — наблюдаемые совпадения и контекст, без сетевого verdict.

## Success Criteria *(mandatory)*

### Measurable Outcomes
- **SC-001**: Для каждого релевантного ACL выводятся все совпавшие правила; ни одно подходящее правило не теряется на фиксированном независимом тестовом наборе.
- **SC-002**: В 100% проверочных сценариев порядок и группировка правил соответствуют сохранённым снимкам.
- **SC-003**: В проверочных сценариях отчёт не содержит единого permit/deny verdict, даже если присутствуют `deny` и `permit`.
- **SC-004**: Прототип запускается полностью на синтетических данных без доступа к сетевым устройствам.
- **SC-005**: Ошибки входного контракта и отсутствие необходимого снимка однозначно отличимы от валидного результата без совпадений (для принятых допущений A-03/A-05).

## Assumptions

- **A-01**: В первом срезе данные релевантности и снимков подаются как готовые локальные fixtures.
- **A-02**: Поднабор правил определяется на проектном этапе, а не навязывается исходной постановкой.
- **A-03**: Отсутствие снимка для явно релевантной пары — ошибка полноты данных, а не «нулевое число совпадений».
- **A-04**: Неизвестный предикат является явной ошибкой входа, а не молча допускаемым правилом.
- **A-05**: При некорректном входе не выдаётся неполный отчет, который оператор может принять за полный.
- **A-06**: Параметры производительности и объём production-снимков не являются критериями данного MVP; оценивается корректность на конечных синтетических наборах.

**Out of scope:** сбор с устройств, vendor-specific синтаксис, маршрутизация, вычисление end-to-end сетевого пути, промышленное хранилище, UI/веб-сервис.
